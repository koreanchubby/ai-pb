# 협업 규칙 (WORKFLOW)

> 두 사람이 같은 저장소 하나만 보고 일하기 위한 약속입니다. **작업 시작 전**과 **작업 끝난 후**에 아래 순서를 꼭 지킵니다.

## 한눈에 보기

```
[시작 전]  Pull → STATUS.md 확인 → Issue 확인 → STATUS.md에 "진행 중" 표시 → 브랜치 생성
[작업 중]  작게 커밋, app.js 수정 전 상대에게 알림
[끝난 후]  Push → Pull Request → STATUS.md에 "리뷰 대기" 표시 → 상대가 실행·승인 → Merge → Issue 닫기 → STATUS.md "완료"
```

## 1. 작업 시작 전 (5분)

1. **WebStorm에서 main을 최신으로 받기**
   - 위쪽 브랜치 이름(`main`) 클릭 → **프로젝트 업데이트(Update Project)** → 확인
2. **`docs/STATUS.md` 읽기**
   - 상대가 지금 무엇을 하고 있는지, 어떤 파일을 건드리는지 확인합니다.
3. **GitHub Issues에서 오늘 할 일 확인**
   - 저장소 상단 **Issues** 탭 → 내게 배정된(Assignee) 이슈를 엽니다.
4. **`docs/STATUS.md`에 내 작업을 "🟡 진행 중"으로 적고 main에 바로 커밋·푸시**
   - 이렇게 해야 상대가 같은 파일을 동시에 고치지 않습니다.
   - **STATUS.md는 둘 다 고치는 파일입니다. 자기 이름이 있는 줄만 고치고, 고치기 직전에 반드시 Pull합니다.** (충돌 방지)
5. **새 브랜치 만들기**
   - 브랜치 이름(`main`) 클릭 → **새 브랜치** → 이슈에 적힌 브랜치 이름 입력 (예: `feat/save-input`)

## 2. 작업 중

- 의미 있는 단위마다 커밋합니다. 커밋 메시지는 무엇을 바꿨는지 한 줄로 적습니다.
  - 예: `feat: 고객 정보 입력값 localStorage 저장`
- **`app.js`는 둘 다 쓰는 파일**입니다. 수정하기 전에 카톡으로 "app.js의 ○○ 함수 수정할게"라고 알립니다.
- `index.html`의 버튼·입력칸 **id는 바꾸지 않습니다.**
- Stitch나 AI가 만든 코드로 **파일 전체를 덮어쓰지 않습니다.** 필요한 부분만 옮깁니다.

## 3. 작업 끝난 후 (10분)

1. **브라우저로 실행해 보고 9단계 끝까지 넘어가는지 확인**합니다.
2. **커밋 → Push** (WebStorm 상단 Git → 커밋 / 푸시)
3. **GitHub에서 Pull Request 만들기**
   - Push 후 저장소 화면에 뜨는 **Compare & pull request** 클릭
   - 본문은 자동으로 나오는 양식(PR 템플릿)을 채웁니다.
   - 본문에 `Closes #이슈번호`를 적으면 Merge될 때 이슈가 자동으로 닫힙니다.
4. **`docs/STATUS.md`에서 내 작업을 "🔵 리뷰 대기"로 바꿉니다.**
5. **상대에게 카톡으로 PR 링크를 보냅니다.**

## 4. 리뷰하는 사람

1. PR 페이지 상단의 브랜치를 WebStorm에서 받아(Checkout) 직접 실행합니다.
2. 확인할 것
   - 9단계(승계 포함)와 7단계(일반 자산관리) 경로가 끝까지 넘어가는가
   - 설문 미완료·전문가 승인 전 다음 버튼이 잠기는가
   - 모바일 폭에서 화면이 깨지지 않는가
   - 계산 함수를 바꿨다면 PR에 변경 전후 숫자가 적혀 있는가
3. 문제가 없으면 **Approve → Merge**, 문제가 있으면 코멘트를 남깁니다.
4. **자기 PR은 스스로 Merge하지 않습니다.**

## 5. Merge 후

- 작성자가 `docs/STATUS.md`에서 해당 작업을 "✅ 완료"로 옮기고 다음 할 일을 적습니다.
- 팀 차원의 결정이 생겼다면 `docs/DECISIONS.md` 맨 위에 추가합니다.
- 두 사람 모두 WebStorm에서 main을 다시 Pull합니다.

## 6. 하지 말 것

- ZIP 파일, 메신저 첨부를 원본으로 쓰기
- "최종", "최종진짜최종" 같은 복사본 파일 만들기 (버전은 태그로 남김)
- `.env`나 API 키를 커밋하기 (`.gitignore`로 제외되어 있음)
- main에 직접 기능 코드 커밋하기 (예외: `docs/STATUS.md` 상태 갱신)

## 7. 충돌(conflict)이 났을 때

두 사람이 같은 파일의 같은 줄을 고치면 Pull이나 Merge 때 **충돌**이 납니다. 당황하지 말고 아래 순서대로 합니다.

**WebStorm에서 Pull했는데 충돌 창이 뜬 경우**

1. "충돌" 창에 파일 목록이 나옵니다. 파일을 고르고 **병합(Merge)...** 버튼을 누릅니다.
2. 화면이 세 칸으로 나뉩니다. 왼쪽 = 내 것, 오른쪽 = 상대 것, 가운데 = 최종 결과.
3. 줄마다 화살표(»/«)로 남길 쪽을 고르거나, 둘 다 필요하면 둘 다 넣습니다.
   - **STATUS.md**: 거의 항상 "둘 다 넣기"가 정답입니다(각자 자기 줄만 고쳤기 때문).
   - **app.js·CSS**: 확신이 없으면 고르지 말고 **취소** → 카톡으로 상대와 상의하거나 Claude에게 "충돌 해결 도와줘"라고 요청합니다.
4. **적용** → 커밋 → 푸시.

**GitHub PR 화면에 "This branch has conflicts"가 뜬 경우**

- 간단한 문서 충돌이면 PR 화면의 **Resolve conflicts** 버튼으로 웹에서 고칩니다. `<<<<<<<`, `=======`, `>>>>>>>` 표시 줄을 지우고 남길 내용만 둔 뒤 **Mark as resolved → Commit merge**.
- 코드 충돌이면 PR 작성자가 WebStorm에서 main을 자기 브랜치로 병합(Merge)해서 위 방법으로 해결합니다.

**충돌을 줄이는 습관**

- 작업 시작 전 Pull, STATUS.md 확인 (같은 파일 동시 작업 피하기)
- PR은 작게, 자주
- `app.js` 수정 전 카톡으로 알리기

## 8. Claude와 사람의 역할 나누기

Claude는 **파일을 읽고 고치는 것**은 잘하지만, **GitHub 로그인이 필요한 일(Push, PR 승인 등)**은 막힐 수 있습니다. 막히면 아래처럼 나눕니다.

| 일 | 누가 | 방법 |
|---|---|---|
| 코드·문서 수정, 원인 설명, 점검 | Claude | 연결된 `ai-pb` 폴더의 파일을 직접 수정 |
| Pull (최신 받기) | 사람 | WebStorm: 위쪽 `main` 클릭 → 프로젝트 업데이트 |
| 커밋 | 사람 | WebStorm: 왼쪽 **커밋** 탭 → 바뀐 파일 체크 → Claude가 제안한 메시지 붙여넣기 → **커밋** |
| Push | 사람 | WebStorm: 위쪽 `main`(또는 브랜치 이름) 클릭 → **푸시...** → **푸시** |
| 브랜치 만들기 | 사람 | WebStorm: 위쪽 `main` 클릭 → **새 브랜치...** → 이름 입력 |
| PR 만들기·승인·Merge | 사람 (Claude가 내용 작성) | GitHub 웹에서. 본문은 Claude가 써 준 것을 붙여넣기 |

> Claude에게 "어디를 눌러야 해?"라고 물으면 위 순서를 한 단계씩 안내합니다.
> 연결 준비: 자기 PC의 `WebstormProjects\ai-pb` 폴더를 Claude 앱에서 **폴더 추가**로 연결해 두세요.
