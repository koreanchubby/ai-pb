## 3. 일하는 흐름 (한 장)

```
이슈(할 일) → 브랜치 만들기 → 작업·커밋 → Push → Pull Request(PR)
→ 다른 팀원이 직접 실행해 보고 리뷰 → Merge → 자동 테스트·배포
```

| 규칙 | 이유 |
|---|---|
| **main에 직접 커밋하지 않고 PR로만 합친다** (예외: `docs/STATUS.md` 상태 갱신, 아래 4절의 자동 작업) | main은 곧 배포본이라 항상 동작해야 함 |
| **PR은 내가 아닌 다른 팀원이 실행해 보고 Approve한 뒤 Merge한다. 자기 PR은 스스로 Merge하지 않는다** | 만든 사람은 자기 실수를 잘 못 봄 |
| **작업 전후로 [STATUS.md](STATUS.md)에 내 줄을 갱신** (🟡 진행 중 / 🔵 리뷰 대기 / ✅ 완료). 내 이름이 있는 줄만 고치고, 고치기 직전에 Pull | 같은 파일을 동시에 고치는 일 방지 |
| `app.js`는 **공유 파일**: 고치기 전에 팀에 알리고 STATUS에서 겹치는지 확인. `index.html`의 버튼·입력칸 **id는 바꾸지 않음**. AI가 만든 코드로 **파일 전체를 덮어쓰지 않음** | 충돌·화면 깨짐 방지 |
| **계산을 바꾸면 같은 입력의 변경 전 → 후 숫자를 PR에 적는다** (PR 양식에 칸이 있음) | 숫자가 왜 바뀌었는지 리뷰어가 확인 |
| **새 기능·숫자(파라미터)에는 논문·공식 자료 근거**를 남기고, 팀 결정은 [DECISIONS.md](DECISIONS.md) **맨 위**에 추가 (인용은 실제로 확인한 것만) | 근거 기반이 우리 앱의 원칙 |
| 리뷰할 때 확인: 9단계(승계 포함)·7단계 경로 완주, 설문 미완료·전문가 승인 전 다음 버튼 잠김, 모바일 폭(약 390px), 계산 변경 시 전후 숫자 | PR 양식의 체크 목록과 같음 |

- **main 브랜치 보호 설정은 꺼져 있습니다.** 초대받으면 main에 직접 Push가 *기술적으로는* 됩니다. 위 규칙은 **약속**이니 꼭 지켜 주세요. (7절 참고)

## 4. main은 혼자서도 움직입니다 — 그래서 자주 Pull

사람이 아닌 것이 main에 직접 커밋합니다. 작업 시작 전·Push 전에 **반드시 Pull**하세요.

| 누가 | 언제 | 하는 일 | 건드리는 파일 |
|---|---|---|---|
| 뉴스 수집 봇 (`news` Actions) | **매시 17분** | 연준·한국은행(ECOS)·FRED·한국투자증권 등에서 지표와 뉴스를 모아 저장 | `data/news.json` (**손으로 고치지 않음**) |
| 하우스뷰 계산 봇 (`house-view` Actions) | `data/house_view_input.json`이 바뀔 때 | 테스트 후 합의 계산 | `data/house_view.json` (**손으로 고치지 않음**) |
| 테스트 (`tests` Actions) | PR을 올릴 때, main에 스크립트·테스트가 들어갈 때 | 단위 테스트 실행 | — |
| 배포 | main에 Push되면 자동 | GitHub Pages가 자동 배포, Eyefeet Cloud는 웹훅으로 자동 배포 | — |
| 유경 님 PC의 예약 작업 | 평일 아침·오후로 만든 것 (마지막 갱신 10/16, 지금 켜져 있는지는 확인 필요) | 원문을 확인해 쓴 뉴스 요약을 PR 없이 main에 올림 (**팀 합의 전 방식**) | `data/news_curated.json` |

- 사람이 매달 직접 입력하는 파일은 `data/house_view_input.json` 하나입니다. 방법은 [HOUSE_VIEW_GUIDE.md](HOUSE_VIEW_GUIDE.md).
- 봇 커밋 때문에 내 브랜치가 뒤처질 수 있습니다. Push가 거부되면 당황하지 말고 Pull(또는 main 병합) 후 다시 Push. 충돌이 나면 [WORKFLOW.md 7절](WORKFLOW.md#7-충돌conflict이-났을-때).

## 5. 꼭 지킬 원칙

- **LLM(생성형 AI)은 비중 숫자나 법률·세무 결론을 정하지 않습니다.** 비중은 테스트된 계산 규칙이 정하고, AI는 요약·설명·위험 신호를 맡습니다. ([PROJECT_BRIEF.md](PROJECT_BRIEF.md) 4장) 이 표현을 더 구체적으로 다듬는 논의는 아직 진행 중입니다.
- **증권사 보고서 PDF·원문은 저장소에 올리지 않습니다.** 점수와 출처 링크만. (저작권)
- 비밀번호·API 키·웹훅 비밀값은 채팅·커밋·문서 어디에도 쓰지 않습니다.
- 화면에서 AI가 쓴 문장은 'AI 작성'으로 표시하고, 매매 지시·비중 숫자를 넣지 않습니다. ([SCREEN_SCENARIO.md](SCREEN_SCENARIO.md)) 화면 흐름 원칙은 [PROJECT_BRIEF.md](PROJECT_BRIEF.md) 3장.

## 7. 합쳐진 팀에서 새로 정해야 할 것 (확인 필요)

지금 문서는 **2인 팀**을 전제로 쓰여 있습니다. 합쳐진 팀에서는 아래를 정해야 합니다. 정해지면 이 표를 지우고 본문·[DECISIONS.md](DECISIONS.md)에 반영합니다.

| 정할 것 | 지금 상태 |
|---|---|
| **새 팀원 역할 분담** | 현재 옥경환: 데이터·기능(입력 저장, 뉴스 수집, DB, 배포) · 이유경: 화면 디자인·UI, 하우스뷰 입력, PR 리뷰. 새 팀원은 **확인 필요** |
| **PR 리뷰어를 누가·몇 명이** | "상대가 리뷰"였던 규칙. 4명 이상이면 리뷰어 지정 방식이 필요 (예: 해당 파일을 맡은 사람 + 1명) |
| **이슈 담당 표기** | 이슈 제목의 `[A]`(화면)·`[B]`(데이터·기능)·`[공통]`은 2인 기준. 확인 필요 |
| **연락 채널** | 지금은 카카오톡. 합쳐진 팀의 채널은 확인 필요 |
| **프로젝트를 어떻게 합칠지** | 다른 팀이 하던 작업물·저장소를 이 저장소에 넣을지, 주제를 하나로 정할지는 교수님 안내와 팀 논의 후 결정. **확인 필요** |
| **eyefeet 마일스톤·간트** | 새 팀원이 우리 마일스톤에 맞출지, 합쳐진 팀 것을 새로 만들지 확인 필요 |
| **합쳐진 팀의 평가 방식** | 교수님이 정한 방식(2인 1조 기준이 바뀌는지)은 확인 필요 |
| **main 보호** | 지금은 꺼져 있음. 켜면 "PR 없이 Push 불가"가 되지만, 자동 수집 봇의 직접 커밋도 막힐 수 있어 설정 방법을 정해야 함 |
| **자동 작업의 사람 점검** | AI가 쓴 시황·요약을 사람이 언제 훑어볼지(예: 주 1회) |
